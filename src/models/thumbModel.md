# thumbModel.py

A `QQuickImageProvider` that serves thumbnails to QML by reading and writing
the shared **freedesktop.org Thumbnail Managing Standard** cache at
`~/.cache/thumbnails`. This is the same cache Dolphin, Gwenview, and GNOME
apps read/write, so thumbnails generated by those apps show up here for
free, and thumbnails this provider generates show up in them.

Handles both still images and video files. Video files that don't already
have a cached thumbnail are handled via `ffmpegthumbnailer` (see
"Video support" below) — **`ffmpegthumbnailer` must be on `PATH`** for
video thumbnail *generation* to work (reading already-cached video
thumbnails works regardless, since that path doesn't touch it at all).

Register it in QML/C++ as an image provider (e.g. `engine.addImageProvider("thumb", ThumbnailProvider())`)
and reference images as `image://thumb/<path-or-file-uri>`.

---

## How it works, at a glance

1. QML asks for `image://thumb/<id_string>`.
2. The provider turns `id_string` into an absolute local path, then builds
   the canonical `file://` URI for that path the same way KDE/GNOME do.
3. It MD5-hashes that URI and checks `~/.cache/thumbnails/{x-large,large,normal}/<hash>.png`
   for an existing thumbnail (cache hit). **This step is identical for
   images and videos** — the freedesktop cache format doesn't care what
   kind of file a thumbnail came from, so a video with an existing cache
   entry (made by e.g. KDE's own `ffmpegthumbnailer`) is read exactly the
   same way an image is.
4. On a miss, it generates a frame itself:
   - **Images** — read/scaled directly via `QImageReader`.
   - **Videos** — `QImageReader` can't decode video, so the file extension
     is checked against `VIDEO_EXTENSIONS` and, if it matches, a frame is
     extracted via `ffmpegthumbnailer` instead (see "Video support" below).

   Either way, the result is returned to QML immediately, **and** written
   into the shared cache (correct tier folder + spec-required metadata) so
   future lookups — by this app or any other — hit the cache instead.

---

## Why the URI encoding is non-trivial

The cache filename is `md5(uri).png`, so the URI string has to match
**exactly**, byte-for-byte, what the original thumbnailer used — including
percent-encoding choices.

Qt's `QUrl(...).toString(QUrl.FullyEncoded)` percent-encodes every character
outside the strict RFC 3986 "unreserved" set (`A-Za-z0-9-._~`). But KDE and
GNOME both generate the cache using `g_filename_to_uri()` (glib), which
follows the older RFC 2396 scheme — that scheme has an extra "mark"
character class left **unescaped**: `- _ . ! ~ * ' ( )`.

Net effect: Qt's own encoder and the actual cache format disagree on
characters like `(`, `)`, `!`, `~`, `*`, `'`. A file named `photo (1).jpg`
would hash to two different values depending on which scheme did the
encoding — so this module implements the RFC 2396 scheme by hand via
`urllib.parse.quote(..., safe="/-_.!~*'()")` instead of trusting Qt's
encoder. This isn't a workaround/guess — it mirrors glib's actual behavior
and has been verified empirically against real KDE-generated cache hashes.

**Known limitation:** if a file has been moved or renamed since its cache
entry was created, the hash will legitimately differ from the current path
— that's correct behavior (the old thumbnail belongs to the old path), not
a bug. There's no way to detect "this is the same file, just moved" from
the path alone.

## Video support

Videos ride the exact same cache-hit path as images (same URI/hash scheme,
same directories) — no special-casing needed there. The gap was purely on
the *generation* side: `QImageReader` has no video codec support, so a
video with no existing cache entry needs a different extraction method.

### `VIDEO_EXTENSIONS: set[str]`
Plain set of lowercase extensions (`.mp4`, `.mkv`, `.webm`, `.mov`, `.avi`,
`.m4v`, `.flv`, `.wmv`) used to route a file to the video path. Kept as an
independent constant here rather than importing from `mediaModel.py`, so
this module has no hard dependency on it — if you're using both in the same
project and want a single source of truth, point one at the other.

### `_is_video(local_path: str) -> bool`
Extension check against `VIDEO_EXTENSIONS`. Case-insensitive.

### `_extract_video_frame(local_path: str, target_size: QSize) -> QImage`
- **Inputs**: source video path, and the target width for the generated
  thumbnail.
- **Output**: a `QImage` of the extracted frame, or a **null** `QImage` on
  any failure — treat this identically to a failed `QImageReader.read()`.
- **Behavior**:
  - Shells out to the `ffmpegthumbnailer` CLI (`-i <input> -o <temp.png>
    -s <width> -f`), then loads the resulting PNG into a `QImage`.
  - `-f` enables ffmpegthumbnailer's built-in **film-strip overlay** (black
    bars + sprocket-hole cutouts) — this matches the visual style KDE's own
    thumbnailer already uses, so thumbnails this provider generates look
    consistent with ones Dolphin/KDE generated. Drop `-f` if you'd rather
    have a plain, undecorated frame instead.
  - ffmpegthumbnailer's own default seek position (10% into the video) is
    used rather than specifying one explicitly — this avoids the common
    issue of frame 0 being a blank/fade-in frame.
  - Requires `ffmpegthumbnailer` on `PATH`. If missing, logs and returns a
    null image immediately (doesn't raise).
  - The subprocess call is timeout-bounded (20s) so a corrupt or oddly
    encoded file can't hang the provider.
  - Temp file is always cleaned up, success or failure.

**Dependency note:** on NixOS, `ffmpegthumbnailer` won't be on `PATH`
unless it's declared in your flake/shell — add it (e.g.
`pkgs.ffmpegthumbnailer`) to whichever `shell.nix`/flake devShell or system
packages list this app runs under. It depends on `ffmpeg`'s libraries
internally but is a separate package from the `ffmpeg` CLI itself.

### `class ThumbnailProvider(QQuickImageProvider)`

**`__init__(self)`**
No inputs. Sets up:
- `self.thumbnails_base` — `Path` to `~/.cache/thumbnails`.
- `self.cache_dirs` — list of `Path`s to check, in priority order:
  `x-large`, `large`, `normal` (largest first, so a bigger cached image
  can always be downscaled to fit a smaller request).

**`requestImage(self, id_string: str, requested_size: QSize, size: QSize) -> QImage`**
Called by Qt/QML, not typically called directly.

- **Input** `id_string`: everything after `image://thumb/` in the QML
  source URL. Accepts either a plain local filesystem path
  (`/home/user/pic.jpg`) or a `file://` URI — both are normalized
  internally.
- **Input** `requested_size`: size QML requested (may be invalid/unset).
- **Output** `size`: out-parameter Qt uses to learn the actual returned
  image's dimensions (set by this method).
- **Returns**: a `QImage` — either loaded from an existing cache PNG, or
  freshly generated from the source file if no cache entry existed (via
  `QImageReader` for images, `_extract_video_frame` for videos). Returns a
  null `QImage` only if generation failed too (unreadable file, missing
  `ffmpegthumbnailer` for a video, corrupt file, etc).

## Internal helpers

### `_local_path_to_thumb_uri(path: str) -> str`
- **Input**: a local filesystem path (string).
- **Output**: the canonical `file://...` URI string for that path, using
  `Path.resolve()` (so symlinks/relative components are canonicalized —
  matters because the original cache entry was almost certainly hashed
  from a resolved path too) and RFC 2396-style percent-encoding.
- Pure function, no I/O side effects beyond `resolve()` touching the
  filesystem to canonicalize the path.

### `_size_tier_dir(base: Path, pixel_size: QSize) -> Path`
- **Input**: `base` cache dir (`~/.cache/thumbnails`), and the *actual*
  pixel dimensions of a generated thumbnail (not the requested size).
- **Output**: the appropriate tier subdirectory `Path`, chosen by the
  longer edge of `pixel_size`:
  - ≤128px → `normal`
  - ≤256px → `large`
  - ≤512px → `x-large`
  - \>512px → `xx-large`
- Classify by the image you actually produced, not what was requested —
  other readers compare against real pixel dimensions when deciding if a
  cached thumbnail satisfies their own request.

### `_save_thumbnail(base, uri, uri_md5, img, local_path) -> bool`
Writes a generated thumbnail into the shared cache, spec-compliantly.

- **Inputs**:
  - `base: Path` — `~/.cache/thumbnails`.
  - `uri: str` — the canonical URI (from `_local_path_to_thumb_uri`),
    embedded in the PNG so other readers can identify what this thumbnail
    is for.
  - `uri_md5: str` — that URI's MD5 hex digest, used as the filename.
  - `img: QImage` — the generated thumbnail to save.
  - `local_path: str` — original source file path, used to read its
    current `mtime`/size for the spec-required freshness metadata.
- **Output**: `bool` — `True` if the file was written successfully,
  `False` on any failure (never raises).
- **Behavior**:
  - Picks the tier directory via `_size_tier_dir`, creating it if needed.
  - Embeds `Thumb::URI`, `Thumb::MTime`, `Thumb::Size` as PNG `tEXt`
    chunks — this lets any spec-compliant reader (including future runs
    of this same provider... though this provider currently doesn't
    re-check mtime itself, see Known gaps below) verify the thumbnail is
    still valid for the current version of the file.
  - Writes atomically: generates a temp file in the same directory, then
    `os.replace()`s it into place, so a concurrent reader never sees a
    partially-written PNG.
  - Sets file permissions to `0o600` per the spec's recommendation.

## Known gaps / things to revisit if reusing this elsewhere

- **No mtime validation on cache hits.** Step 1 of `requestImage` treats
  any existing file at the hashed path as valid, without checking its
  embedded `Thumb::MTime` against the source file's current mtime. If a
  file is edited in place (same path, new content) without its mtime
  changing in a way you check for, you'll get a stale thumbnail. Add an
  mtime comparison in the hit-check loop if that matters for your use case.
- **No `fail/` tier handling.** The spec also defines a `fail/<app-name>/`
  directory for caching "this file can't be thumbnailed" so apps don't
  keep retrying known-bad files. Not implemented here.
- **No cache eviction.** Nothing here ever deletes old/orphaned entries —
  matches default KDE behavior (KDE has no built-in cache size/age limit,
  unlike GNOME), but worth a periodic external cleanup job if the cache
  grows large.
- **No control over which video frame other thumbnailers picked.** If a
  video already has a cache entry from another program (e.g. KDE's own
  `ffmpegthumbnailer`), this provider just displays it as-is — it never
  regenerates a thumbnail that already exists. If that pre-existing
  thumbnail looks wrong (e.g. a blank/white frame baked into the PNG
  itself, typically from a fade-in or intro frame the other thumbnailer
  picked), that's a property of the cached file, not something this
  provider's read path can fix. The `_extract_video_frame` seek-to-10%
  heuristic here only applies to thumbnails *this* provider generates from
  scratch; it has no effect on entries that already exist.
